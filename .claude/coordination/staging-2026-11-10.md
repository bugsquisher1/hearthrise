# Staging: the shape, the tooling, the release flow, the runbook (2026-11-10, lane/a-staging)

**Why.** Three releases in one night put a server change on production hours before its client reached players (GitHub's queue, then four failed Pages deploys). Players saw a wrong Level. CLAUDE.md §3.7 already requires the play gate "before `main`, on a staging origin with the QA account signed in". Nothing below spends anything or creates anything: it is built so staging exists the hour the spend is approved.

Marks: ✅ measured or executed here · ⚠ assumed, cannot be proven until the project exists.

Which project a page plays is decided by its **origin**, and which origins a function admits by the **project it runs on**: never a setting, so the same client bytes and the same edge bundle are what get rehearsed and what ship.

## 3. The site: a second GitHub Pages site on `staging.hearthrise.net` ($0)

| Option | Needs | Verdict |
|---|---|---|
| **A second public repo `bugsquisher1/hearthrise-staging` + Pages + custom domain** | the repo, Pages from its `site` branch, one DNS record | **Recommended.** Same host, CDN and cache rules as production, so the rehearsal also rehearses the Pages deploy that failed last night |
| A `staging` branch or a `/staging/` folder in this repo | nothing | **Rejected.** Pages serves one site per repo, and a folder would share production's **origin**: the same localStorage (session tokens), the same service worker scope, the same CSP. Origin is what keeps the two apart |
| Cloudflare Pages / Netlify (free) | a new account, a GitHub app on the repo | Works (`hearthrise-staging.pages.dev` also carries the label). Different CDN and headers than production, so a lesser rehearsal. The fallback if Pages stays unreliable |

**Yes, the domain can carry `staging.`** The one record Tyler adds where hearthrise.net's DNS lives: `staging   CNAME   bugsquisher1.github.io.` Without the custom domain the staging repo would be served under `bugsquisher1.github.io`, which is a **production** origin (`playerHosts`), so the custom domain is required, not cosmetic.

**The host-name rule (in code, both sides):** a staging host carries `staging` in a label of its name and is on the list; no production host does. A host that says staging and is not listed plays nothing. Today the list is `https://staging.hearthrise.net` (`STAGING_ORIGINS`, client and `cors.js`); another host is a one-line data change in both, held equal by `tests/staging-origin.mjs`.

| The mark | `src/app/staging-mark.js`, `src/data/text/staging.js`, `app.css .staging-mark` | a fixed plate "STAGING" on every screen, plus "Nothing you do here is kept." on the account screens, and the tab's name. Takes no room and no press, so staging lays out exactly as production |

## 5. The release flow with staging (proposed CLAUDE.md wording; CLAUDE.md is not edited here)

> **§2, replacing the "Production DB writes" line:** DB writes only via `node tools/apply-migration.mjs <file> --env staging|production`: one file per call, never inside `begin/commit`, never by an agent. A write with no `--env` refuses. Staging goes first: production refuses bytes staging has not run, and `--skip-staging="<why>"` is a stated decision that goes in the report.
>
> **§3.3, every lane, new first bullet:** **Staging first, then production together.** For a release: (1) apply the release's migrations with `--env staging`, in order; (2) if `supabase/functions/**` moved, `node tools/deploy-edge.local.mjs --deploy --env staging`; (3) push `release/vX.Y.Z` to GitHub and put it on the staging site (`node tools/deploy-staging-site.local.mjs X.Y.Z --push`); (4) while the GitHub run judges, `node tools/release-check.local.mjs X.Y.Z --env staging` must say "staging carries this release", `node tests/live-hash-drift.mjs --live --env staging` must be green, and the play gate is played on `https://staging.hearthrise.net` as the QA account; (5) only when the run is green and the play is played: production apply (`--env production`), production edge deploy, `git push origin main`, back to back, then `release-check X.Y.Z` on production. A server change never waits on production for its client: if step 5 cannot finish in one sitting, it does not start.
>
> **§3.3 lane C, replacing "Lane C applies don't wait for a release" (§3.3a):** a reviewed migration applies to **staging** when ready; it reaches production only inside step 5 of the release that carries its client half. A migration with no client half (a prune, an index, a rate) is its own release of one.
>
> **§9, tools line:** every project tool takes `--env staging|production` and prints the project first; `node tools/staging-bootstrap.local.mjs status|parity` reads staging beside production.

**How this removes last night's failure.** The server half used to go to production when it was ready and then wait on GitHub and Pages for its client. Now the waiting happens with the server half on staging. Production's server and client move in one sitting, after the run is green and the site build is known good, so the gap between them is the length of step 5.

**What it costs per release** ⚠ (estimates, to be measured on the first three releases): staging apply 1 to 2 min, staging edge deploy 1 min, staging site push + Pages build 2 to 4 min, all inside the 30 to 60 min the GitHub run already takes; the play gate is the one that already exists, moved earlier. Added wall time: **0 to 5 min**. Step 5 itself: 3 to 6 min, during which production's server is ahead of its client (was: hours).

## 7. What only works once the project exists ⚠

- Every network call of `tools/staging-bootstrap.local.mjs` has run against a fake network only (order, targets, bodies, refusals: `tests/tool-env.mjs`). The Management API shapes for `/secrets`, `/config/auth`, `/config/database/pooler` and the CLI's `--remote` with a second ref are from the docs and the restore runbook, not from a run.
- **The chain has never been replayed on a real Postgres 17.** PGlite (PG 18) replays it on every push; production got it file by file. Step 5 is the first real rebuild, and step 6 its proof. Expect one or two files to need a look. That is a durability result worth the $10 on its own: the restore runbook's "repo rebuild" path stops being a rumour.
- New Supabase projects may ship with fewer default grants than production was created with (docs, 2026). `prepare` grants the legacy defaults the chain revokes from; `parity` prints production's and staging's default ACLs side by side.
- Replay time, Pages build time on the staging repo, certificate issue time: unmeasured.
- Tools outside this lane's list (`vitals`, `economy-watch`, `triage-bugs`, `gm-allow`, `moderate-name`, `access-allow`'s lookup, the load probes) still name production in their own source. They cannot reach staging by accident; they get `--env` when someone needs them there.
- Phone sign-in screen (667 x 375): the plate overlaps the card's top frame by about 12 px. Desktop is clean. The author's look does not count: the visual gate reads it.
- The three staging sentences in `src/data/text/staging.js` need the reader pass (they are never shown on the live site).

## 8. Capacity, durability, observability

- Staging at 1 QA account: the chain's catalogues plus one hero, tens of MB ⚠; Micro's 60 connections hold the engine role's limit of 20 ✅ (role shape copied from production).
- Staging has **no backups that matter and needs none** (disposable; rebuilt from the repo in an hour). Production's durability posture is unchanged by this lane: daily backups, 7 days, PITR still a separate spend, restore still not rehearsed. Staging's replay rehearses the schema half only, never the rows.
- Healthy staging, numerically: `live-hash-drift --live --env staging` exit 0; `staging-bootstrap parity` 0 differences; `hunt-health --env staging` tick fired within 10 s; `release-check X.Y.Z --env staging` "staging carries this release".
- Watch on production after the first week of the new flow: minutes between production apply and Pages serving the release (target under 10; was hours on 11-10).
