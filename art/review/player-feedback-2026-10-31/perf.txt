HEARTHRISE — PLAYER FEEDBACK, 2026-10-31
Panelist: the old-laptop player (lane/f-perf)

Who I am: six-year-old budget laptop, integrated graphics, 8 GB of RAM, a dozen tabs open, slow
connection, sometimes Firefox. I notice every stutter and every time the fan spins up, and I quit games
that make the machine crawl. Unlike the rest of the panel I measure as well as feel, and I put the
numbers next to how it felt. Browser window 1366x768, mouse and keyboard, no touch.

IN SHORT: quick to load on a good line and smooth on a fast CPU, but on my laptop (CPU x4) the world
canvas eats 99% of the main thread even when the town is perfectly still, hunts run ~30 fps with
hitches, a slow line shows 9-40 s of plain black before sign-in, every patch re-downloads all 7.5 MB,
and inside hunts each hero hop / bag open leaks ~300-1,100 DOM nodes. Ranked list in section 15.
Scores: load 6/10, smoothness 5/10, restraint with my machine 3/10.

HOW I PLAYED AND MEASURED (read this before trusting any number)
- The real play.html + src/ on 127.0.0.1 via tools/qa/local-world.mjs (the replayed server chain, the
  real hr-accrue engine, real sign-up screens). Branch = origin/main + lane/t-local-world +
  claude/upbeat-einstein-mrh0ig + claude/serene-tesla-7txs5f, all three merged with no conflict.
  live version string: 0.2.74.
- Browser: Chromium 153 (headless, the sandbox's own build). No Firefox in this sandbox, so every
  Firefox remark below is a guess, not a measurement.
- My laptop is simulated with Chrome's CPU throttle: x1 = the sandbox (Xeon 2.8 GHz vCPU, roughly a
  decent desktop core), x4 = my laptop on a normal day with a dozen tabs, x6 = my laptop when it's hot
  and the tabs are busy. Network: DevTools "Fast 3G" (562 ms RTT, 1.44 Mbps down, 675 kbps up) for the
  slow-connection runs.
- WHAT THE LOCAL SERVER FLATTERS: the server is on the same machine, so every RPC and engine call costs
  ~0 ms of distance (real Supabase from Europe/US is 40-150 ms per round trip, more on my connection).
  It serves files UNCOMPRESSED and over HTTP/1.1; GitHub Pages gzips text and speaks HTTP/2, so I give
  both "bytes on the wire here" and "gzip estimate" for text files. Images don't compress, so the PNG
  numbers are real. Every "server ms" number below is a floor, not a forecast.
- WHAT THE SANDBOX PUNISHES: there is no GPU here. Canvas drawing is done in software on the CPU, which
  is pessimistic next to even a weak integrated GPU. So I trust main-thread task time and long tasks
  more than fps, and I say which is which.
- Instruments: Long Tasks + Long Animation Frames observers (with script attribution), rAF frame
  times, Chrome's Performance metrics (JS heap, DOM nodes, listeners, task time), a sampling CPU
  profile for "what is on the main thread", and a byte counter on the local server's sockets (catches
  everything, the service worker and the push socket included).

1. COLD FIRST LOAD -> SIGN-IN SCREEN
────────────────────────────────────────────────────────────────────────────────────────────
What I did: opened play.html in a brand-new browser profile (empty cache) and waited for the sign-in box.

How it felt: on a normal line it's quick. The logo and the box appear together, nothing jumps around.
On my slow line it's a black screen. No logo, no "loading", no progress, nothing: a flat near-black
page (rgb 10,11,14) until the whole game has arrived, then the sign-in box pops in. At the 8-second mark
I took a picture: 100% black. I would have hit refresh at least once, which restarts it.

Numbers (time to sign-in box visible / first paint / long tasks before it):
  CPU x1, local net ......  1.1 s / FCP 1.04 s / 2 long tasks, worst 56 ms, 109 ms total
  CPU x4, local net ......  2.2 s / FCP 1.72 s / 3 long tasks, worst 261 ms, 522 ms total
  CPU x6, local net ......  2.8 s / FCP 2.41 s / 5 long tasks, worst 331 ms, 821 ms total
  CPU x1, Fast 3G ........ 40.2 s / FCP 39.7 s  (nothing painted before the box)
  CPU x4, Fast 3G ........ 40.0 s / FCP 40.0 s  (network-bound; the CPU hardly matters here)
What it downloads before the sign-in box: 359 requests, 4.19 MB on the wire here.
  346 JavaScript modules = 3.96 MB raw (~1.39 MB gzipped), 8 stylesheets 240 KB (~65 KB gz),
  play.html 27 KB, the 273 KB logo PNG. The whole game's code, its data tables (monsters.js 73 KB,
  items.js 67 KB, hunt-tutorial.js 81 KB, item-descriptions.js 45 KB, hunt-grounds.js 44 KB, the
  crafting simulator, the hunt engine) are all fetched to show an email box and a password box.
Main thread before the box at x4: 1.46 s of task time, 303 ms of it script compile/run.
Caveat that FLATTERS the slow-line number in your favour on Pages, and one that hurts it here: this
  local server is HTTP/1.1 with no gzip, so 359 requests queue 6 at a time behind a 562 ms RTT. The
  import graph is FLAT (343 of 359 requests are started straight from play.html, max chain depth 3),
  which is genuinely good: on Pages (HTTP/2 + gzip) this load is bandwidth-bound, about 1.5 MB, so my
  estimate for Fast 3G there is ~9-12 s of black screen, not 40. Still 9-12 s of black.
Fix value: a painted shell (logo + "Loading Hearthrise..." + a bar) in play.html costs nothing and
  turns the black wait into a wait I believe in. Loading only the sign-in screen's code first and the
  rest while I type would cut the pre-sign-in download from ~1.5 MB gz to a few hundred KB (-70-80%,
  ~7-9 s saved on Fast 3G).

4. RELOAD, CACHED SECOND LOAD, AND WHAT DOWNLOADS AFTER AN UPDATE
────────────────────────────────────────────────────────────────────────────────────────────
What I did: reloaded while in town (it brings me straight back into town, signed in, same hero -
good). Then, because the local server sends "no-store" and there's no service worker (only a kill
switch script), I made the local server answer like GitHub Pages (max-age=600 + Last-Modified/304) from
my scratch harness, in a context with Playwright routing off (routing disables the HTTP cache), and
measured: first visit, reload, and a reload right after a simulated release (every ?v= string and the
build version bumped, nothing else changed).

How it felt: the reload is quick and lands me where I was. The update is a second cold start.

Numbers (reload -> standing in town, local net):
  reload, CPU x1 ......... 1.8 s     reload, CPU x4 ......... 3.5 s     reload, CPU x6 ......... 4.9 s
  Cached reload (Pages-like headers): 400 requests, 384 from cache, 16 over the network, 42 KB (all
    API). Excellent - a warm visit costs almost nothing.
  After a release: 389 of 400 files re-downloaded, 7.46 MB (~4.3 MB gz-equivalent). Only 11 small
    unversioned UI PNGs stayed cached. Every atlas (2.9 MB of unchanged pixels), the vendored
    supabase-js-2.103.0 (183 KB, already versioned in its own file name), the logo, glyphs.js: all of
    it comes again. On Fast 3G that's ~25 s of download per patch, and you ship patches daily.
  "Came back after 10 minutes" (cache stale, simulated with max-age=0): 395 requests, 368 of them 304
    Not Modified, 110 KB total. On HTTP/2 that's a couple of round trips, cheap in bytes. Fine.
Fix value: version each file by its own content hash (or only bump what changed) - saves ~7 MB raw /
  ~4 MB gz per release for a returning player, i.e. ~95% of the post-update download when only code
  changed, and all 2.9 MB of atlases when art didn't change.

5. STANDING IN TOWN, AND WALKING THROUGH IT
────────────────────────────────────────────────────────────────────────────────────────────
What I did: stood still in Havora with the mouse resting, then clicked around to walk.

How it felt: at x1 it's a calm, pretty scene. At x4 (my laptop) standing still already feels heavy:
the fan would be on and the other tabs would get sluggish, and walking is visibly choppy, about 25 fps
with hitches when the camera pans. At x6 walking is a slideshow (14-23 fps, hitches of 120-170 ms).
The worst part is that NOTHING is happening on screen while it works this hard.

Numbers, standing still (12 s windows, one hero):
            fps    frame p50/p95/max     frames>50ms  long tasks (worst)   main thread busy
  x1 ...... 60     16.7 / 16.7 / 33          0          0                  37%
  x4 ...... 31     33 / 50 / 83              7          2 (58 ms)          99%
  x6 ...... 18     50 / 67 / 100            90        115 (91 ms; 6.4 s of long tasks in 12 s)  99%
  During one accidental 3-minute stay in town at x4 the main thread was busy 129 s out of 180 s.
  The picture: the repo's own pane-probe saw the town image change in 1% of samples; one still span of
  9.9 s out of 10. So the game repaints an unchanging picture 60 times a second.
  What's on the main thread (CPU profile, x4, 8.6 s): drawImage 49.8%, native raster "(program)" 39.5%,
  canvas-backend.js 2.9%, world-boot.js 1.1%. Long-animation-frame attribution: world-boot.js frame()
  (rAF), then shell.js patchComponents (a setInterval), then town-presence.js (setInterval).
  Why it costs so much: each frame blits 3.18 million pixels = 3.6x the 1350x655 canvas. 7 big blits a
  frame: four 512x512 ground chunks composed into a 740x393 buffer, two full copies of that buffer, then
  the buffer scaled onto the screen canvas. 29-48 drawImage calls a frame in total. No smoothing (good,
  crisp pixels).
  Server traffic standing still: one hero alone, 30-50 requests/min (hr_town_view every ~2 s), ~20 KB/min.
  With my two heroes and two friends in town: 125 requests/min (hr_town_view 90/min, hr_town_move
  18/min), 59 KB down and 158 KB UP per minute (every request carries the ~1 KB auth token).
Numbers, walking (two 5 s walks per rate):
  x1 ...... 48-51 fps, p95 33 ms, max 50, 0 long tasks, busy 54%
  x4 ...... 23-27 fps, p95 67 ms, max 100, 49 frames>50 ms in 10 s, 42 long tasks (worst 107), busy 96%
  x6 ...... 14-23 fps, p95 67-117 ms, max 167, 78 long tasks (worst 139), busy 97%
  Profile while walking at x4: drawImage 49.7%, raster 36.1%, all of the game's own JS < 5%.
  hr_town_move ~1/s and hr_town_view ~1.5/s while walking.
Software-rendering caveat: this sandbox has no GPU, so every blit is CPU work. On a laptop where Chrome
  gives the canvas the integrated GPU, much of the drawImage cost leaves the main thread, but the GPU
  then does the same 190 million pixels a second, which is exactly what spins my fan and drains my
  battery. And Chrome blocklists plenty of old Intel drivers, which puts those laptops on this exact
  software path.
Fix value: only redraw when something changed (or cap a still town at ~10 fps), and keep the composed
  ground buffer until the camera moves. Standing in town would drop from 37% to a few % of one core at
  x1, from 99% to maybe 10-20% at x4. This is the single biggest "be kind to my machine" win.

  Back, x4: picture moving in 27 ms; first 5 s at 27 fps, 12 long tasks (836 ms), worst 109 ms

14. DOES IT LEAK OVER A LONG SESSION?
────────────────────────────────────────────────────────────────────────────────────────────
With time alone: no. 60 idle seconds in a hunt added 3 DOM nodes; the GC'd heap grew 4.3 MB in 36
minutes and levelled off (17.1 MB at 30 min, 16.7 at 36). Task time crept up ~6 points.

With actions, inside a hunt: YES. Straight after the long session, on the same page, after forced GC:
  10x open/close the bag in a hunt ......... +5,372 DOM nodes  (~537 per open), listeners unchanged
  10x open/close Character in a hunt ....... +2,791 DOM nodes  (~279 per open)
  10x hop between my two heroes ............ +10,807 DOM nodes (~1,080 per hop) and +350 listeners
                                             (+35 per hop)
  The live document stayed at ~1,200 elements the whole time; the rest is detached DOM that something
  still holds. In town (earlier world) 40 window opens added exactly 0 nodes, so it's something
  hunt-only: the views that draw the hunt for the hero on screen, rebuilt and never let go.
  An evening of 200 hops and 200 bag opens would leave ~320,000 orphaned nodes and ~7,000 listeners.
  That's the kind of memory that pushes my 8 GB laptop into swap and makes GC pauses show up as
  hitches after a couple of hours.

────────────────────────────────────────────────────────────────────────────────────────────
15. TOP TEN THINGS SLOWING THIS GAME FOR A REAL PLAYER (ranked for my laptop)
────────────────────────────────────────────────────────────────────────────────────────────
 1. The world repaints a still picture 60 times a second. Town standing still: 37% of the main thread
    at x1, 99% at x4 (31 fps), 99% at x6 (18 fps, 115 long tasks in 12 s); the picture changed in 1%
    of samples. Fix: draw only on change / low idle frame rate. Saves ~30 points of a core at x1 and
    ~80 points at x4 while idle; fan off, other tabs usable.
 2. Every frame rebuilds the whole ground: 3.18 M pixels blitted per frame, 3.6x the canvas (four 512x512
    chunks -> 740x393 buffer, two buffer copies, scale to screen). drawImage + raster = 80-90% of every
    profile; the game's own JS < 5%. Hunt at x4 33 fps p95 50 ms, x6 16 fps p95 100 ms; walking x4
    23-27 fps. Fix: keep the composed ground until the camera moves, draw sprites over it: roughly
    -60% pixels per frame (my estimate: x4 hunts near 50-60 fps).
 3. Detached DOM leaks per action in hunts: ~1,080 nodes + 35 listeners per hero hop, ~537 nodes per bag
    open, ~279 per Character open, never freed. Fix: let the old views go. Saves all of that growth
    (~320k nodes in a heavy evening).
 4. Black screen on a slow first visit: 346 JS modules (3.96 MB raw / ~1.39 MB gz) load before the sign-in
    box, nothing is painted until then: 40 s here (HTTP/1.1), ~9-12 s estimated on Pages over Fast 3G.
    Fix: paint a shell in play.html and load the game behind sign-in: ~1 MB gz / ~6-8 s less before
    I can type, and something on screen in ~1 s.
 5. Every release re-downloads the whole game: 389 of 400 files, 7.46 MB raw (~4.3 MB gz), including
    2.9 MB of unchanged atlases. ~25 s per patch on Fast 3G. Fix: per-file content hashes: ~4 MB saved
    per patch when only code changed.
 6. A hidden tab keeps working at full rate: 64 calls and 1.45 MB in 2 minutes hidden, ~10% of my main
    thread at x4; in the long session 13-14 requests and ~290 KB a minute while hidden. Fix: pause polls
    when hidden, one catch-up on return: ~95% of background traffic and CPU.
 7. Every world atlas downloads at sign-in (2.9 MB PNG: havora 1.2 MB, common 573 KB, hunt 547 KB...),
    so "Loading the world..." sits for 13.5-15.4 s on Fast 3G for a brand-new hero. Fix: load per area,
    recompress pixel-art PNGs: maybe 1-1.5 MB and 5-8 s less on a slow line.
 8. Every engine reply is the full character (28-50 KB raw, ~6.7 KB gz), even "accrued:false,
    below_min_span": 4-5/min solo, 17/min in a party of four (549 KB/min raw). Parsed and applied on my
    main thread each time. Fix: deltas or "unchanged since version N": ~80-90% fewer bytes and less JSON.
 9. Town presence polling: hr_town_view every ~2 s standing still, ~0.7 s walking; 125 requests/min with
    two heroes and two friends nearby, 158 KB/min of upload (headers). On a 560 ms line these queue. Fix:
    push presence or poll slower when nothing moves: most of those requests.
10. Main-thread spikes on hops and hunt entry: hop 0.6 s at x4 / 1.0 s at x6 (atlas.js 101-208 ms
    tasks, forced clientWidth layouts); Enter 1.1 s at x4 / 1.9 s at x6 (session/server.js 131-189 ms
    applying the hunt). Plus shell.js patchComponents on a timer (~3% of a hunt) and ~63 style
    recalculations a second. Fix: cache per-hero scenes, split big applies: ~0.5 s per hop at x4.

────────────────────────────────────────────────────────────────────────────────────────────
16. WHAT'S ALREADY GOOD
────────────────────────────────────────────────────────────────────────────────────────────
- The game's own JavaScript is lean: under 5% of the main thread in every profile I took; window click
  handlers 33-59 ms even at x4. The cost is pixels, not logic.
- The import graph is flat (max depth 3), so a slow line isn't also a waterfall.
- A warm revisit costs 42 KB with ordinary cache headers, and reload puts me back exactly where I was
  (town, or the same hunt with both heroes): 1.8 s x1, 3.5 s x4.
- In town, windows are built once and reused: 40 open/close cycles, zero new nodes. JS heap stays small
  (11-23 MB) for everything on screen.
- No console errors in any page I checked (every cold load, the friends' tabs, the 36-minute
  session); nothing ever tried to leave the machine.
- Coming back to the tab is instant: picture moving within 13-27 ms.
- Hunts genuinely run on the server: with the tab hidden my CPU dropped to 2% and the hunt kept going.
- Bandwidth for watching a solo hunt is modest: ~1.6 MB/hour gzipped.
- Loading messages where it matters ("Reading your characters...", "Loading the world...").
- Crisp pixels (no smoothing anywhere), no layout jumps, the name-taken message is clear.

────────────────────────────────────────────────────────────────────────────────────────────
17. WOULD MY LAPTOP'S OWNER KEEP PLAYING?
────────────────────────────────────────────────────────────────────────────────────────────
Yes, but only in short visits with the tab closed in between, which is backwards for a semi-idle game
whose promise is "leave it open and watch". On my laptop the town alone pins a core (99% at x4) and
keeps the fan going while nothing on screen moves, and the dozen other tabs would crawl. On a hot day
(x6) hunts run at 16-24 fps with 100-200 ms freezes, so I'd stop watching. What keeps me: the server
keeps hunting when I close the tab, the first load on a decent line is quick, and the loop is good. I'd
tell friends with old laptops "play it, but don't leave it open", and that's the sentence you don't
want in a review of an idle game.

THE ONE THING I'D TELL THE DEVS: stop painting when nothing changed. The canvas redraws an identical
town 60 times a second (37% of a fast core, all of mine). Draw on change, or at a low idle frame rate,
and you fix the fan, the battery, the other tabs and most of the x4/x6 choppiness in one change.
